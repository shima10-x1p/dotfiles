# Model Task Router

## Purpose

開発タスクを、難易度ではなく「判断量」「影響範囲」「検証可能性」「失敗時の影響」で分類し、次のどれに任せるべきかを判定する。

- `GPT-5.4 mini`: 判断より作業が中心で、範囲と完了条件が明確なタスク
- `GPT-5.3-Codex`: コードベースを読んで実装判断する必要がある開発タスク
- `GPT-5.4以上の最上位モデル`: 曖昧さの整理、設計、リスク評価、重要判断が必要なタスク

`GPT-5.4以上の最上位モデル` は固定モデル名ではなく、現在利用できる最上位モデル枠として扱う。将来 GPT-5.5 以降が出た場合も、この枠に置き換えて判定する。

## Workflow

1. ユーザーのタスクから、目的、背景、対象範囲、実装方針、完了条件、検証方法、失敗時の影響、重要領域への関与、不明点を抽出する。
2. 情報が足りなくても質問で停止せず、明示された情報から暫定判定する。
3. 認証、認可、課金、セキュリティ、個人情報、機密情報、DBスキーマ変更、不可逆マイグレーション、本番障害、データ損失、外部API仕様変更、公開APIの破壊的変更、テストだけでは正しさを確認できない変更があれば、mini には割り当てない。
4. 影響範囲が広い、設計判断が必要、失敗時の影響が大きい、検証が難しい場合は最上位モデル枠へ上げる。
5. 判定と reasoning effort、信頼度、不足情報、上げ下げ条件、次アクションを出す。

詳細な判定基準、代表例、reasoning effort の目安は [model-routing-guide.md](references/model-routing-guide.md) を読む。

## Expected Input

入力として次を想定する。すべて揃っていなくてもよい。

- タスクの目的
- 背景
- 変更対象ファイルまたは対象範囲
- 実装方針が決まっているか
- 完了条件
- テストや検証方法
- 失敗時の影響
- セキュリティ、認証、認可、課金、DB、本番環境への関与
- 不明点や制約

重大リスクが不明な場合は、不足情報に `要確認` として明記する。

## Output Format

必ず次の形式で回答する。

```text
判定: <GPT-5.4 mini / GPT-5.3-Codex / GPT-5.4以上の最上位モデル>
reasoning effort: <low / medium / high / xhigh>
信頼度: <高 / 中 / 低>

理由:
- ...
- ...
- ...

mini に落とせる条件:
- ...

Codex に上げる条件:
- ...

最上位モデルに上げる条件:
- ...

不足している情報:
- ...

推奨する次のアクション:
- ...
```

`mini に落とせる条件`、`Codex に上げる条件`、`最上位モデルに上げる条件` は、該当がなければ `なし` と書く。

## Judgment Stance

- モデル性能だけでなく、失敗時の影響で判断する。
- 難易度ではなく、判断量、影響範囲、検証可能性を見る。
- 小さな変更でも、認証、課金、DB、本番障害なら慎重に扱う。
- 大きな変更でも、仕様と手順が固まっていて検証可能なら GPT-5.3-Codex に落とせる可能性を考える。
- 最上位モデルは責任の置き場所ではなく、判断材料を作る場所として扱う。
- 不明点を勝手に確定しない。
- 些細な不明点だけで質問停止しない。
- 暫定判定と要確認事項を分けて出す。
