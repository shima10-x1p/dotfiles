# Model Task Router

## Purpose

開発タスクを読み、次を判定する。

1. タスクの種類
2. 難易度
3. サイズ
4. 複雑さ
5. 失敗時の影響
6. 推奨モデル
7. 必要な昇格先モデル
8. 実装へ落とす場合の担当モデル
9. その判断理由

モデル選定は「難しそうか」ではなく、次の最大値で決める。

```text
推奨モデル =
  max(
    作業範囲の広さ,
    判断の重さ,
    失敗時の痛さ,
    不確実性,
    既存構造を読む必要性
  )
```

コード量ではなく、判断を間違えたときの被害を重く見る。typo 修正は複数ファイルでも軽い。一方で、例外処理方針、認証・認可、DB移行、サービス分割、ユーザー情報統合は、コードを書いていなくても重い。

## Workflow

1. 入力タスクから、目的、対象範囲、仕様の確定度、既存コード・ADR・仕様の読解要否、完了条件、検証方法、失敗時の影響、重要領域への関与、不明点を抽出する。
2. まず5分類のどれかに置く: `定型作業`、`局所実装`、`構造を読む実装`、`設計・分解`、`高リスク判断`。
3. 難易度、サイズ、複雑さ、リスクを `低`、`中`、`高`、必要なら `中〜高` のように判定する。
4. 認証、認可、課金、セキュリティ、個人情報、DB移行、不可逆変更、本番障害、サービス境界、ユーザー情報統合、仕様とADRの矛盾があれば安全側に倒す。
5. 仕様とADRがある場合は、実装だけと短絡せず、整合性と実装順序の判断が必要かを確認する。
6. 推奨モデル、昇格先モデル、実装担当モデルを分けて出す。設計判断は GPT-5.4 または GPT-5.5、実装へ落とした後は GPT-5.3-Codex または GPT-5.4 mini になることがある。
7. 巨大な実装タスクは、そのまま下位モデルへ投げず、レビュー可能、テスト可能、完了条件が明確な単位へ分割するよう注記する。

## Task Types

| 分類 | 説明 | 主な推奨モデル |
|---|---|---|
| 定型作業 | 仕様が明確で、機械的に直せる作業 | MAI-Code-1-Flash |
| 局所実装 | 1画面、1API、1関数などに閉じる小さな実装 | GPT-5.4 mini |
| 構造を読む実装 | 既存構造を読んで複数ファイルに実装する作業 | GPT-5.3-Codex |
| 設計・分解 | 仕様、ADR、MVPを実装順に落とす作業 | GPT-5.4 |
| 高リスク判断 | 本番障害、認証認可、サービス分割、データ統合 | GPT-5.5 |

## Model Guide

### MAI-Code-1-Flash

軽量な定型作業に使う。

向いているタスク:

- README の追記
- typo 修正
- ログ文言の軽い統一
- テスト名の変更
- 小さな説明文の修正
- 仕様が完全に決まっている単純な置換

判断基準:

- 仕様が明確
- 影響範囲が狭い
- 失敗しても戻しやすい
- 既存設計を深く読む必要がない
- セキュリティ、認証、DB、サービス境界に触れない

避けるタスク:

- 複数ファイルにまたがる意味のある実装
- API設計
- DB設計
- 認証・認可
- 本番障害調査
- アーキテクチャ判断

### GPT-5.4 mini

局所的な実装や小さめのコード探索に使う。

向いているタスク:

- フォームの必須項目エラー表示
- APIレスポンスに1項目追加
- CSSやテンプレートの局所的な表示崩れ修正
- 小さな正常系テストの追加
- 作成日時による一覧ソート追加
- 小さな設定追加
- 影響範囲が明確な軽いバリデーション追加

判断基準:

- 1画面、1API、1機能の中で閉じる
- 仕様がほぼ決まっている
- 既存構造を少し読むだけでよい
- 失敗しても戻しやすい
- 設計判断より実装作業が中心

昇格条件:

- 複数層にまたがる
- UseCase、Service、Repository、DBまで触る
- 仕様の解釈が必要
- セキュリティ上の判断が必要
- 既存設計を崩す可能性がある

昇格先は、実装中心なら GPT-5.3-Codex、設計判断が必要なら GPT-5.4。

### GPT-5.3-Codex

既存コードを読んで、複数ファイルにまたがる実装を進める主力モデルとして使う。

向いているタスク:

- FastAPIに新しいエンドポイントを追加し、UseCase経由で処理する
- CSVを読み込みDBへ登録するバッチ処理を作る
- 画像アップロードにファイルサイズ・拡張子チェックを追加する
- ECサイトに在庫切れ商品の表示制御を追加する
- EXIF読み取り処理を別プロジェクトやCore層へ分離する
- 共通例外ハンドリングの実装
- ページネーション追加
- 古いライブラリ利用箇所を新しいAPIへ置き換える
- テスト追加を含む中規模実装

判断基準:

- 既存コードを読んで実装する必要がある
- 複数ファイルにまたがる
- テストも合わせて追加・修正する
- 仕様はある程度決まっている
- 実装中心だが、軽い設計判断も必要
- アーキテクチャ方針そのものは決めない

避けるタスク:

- 認証・認可モデルの再設計
- サービス分割方針の決定
- 本番障害の初期調査
- MVP全体のタスク分割
- 仕様とADRの矛盾解消
- 大きなアーキテクチャ判断

### GPT-5.4

設計、分解、方針決定に使う。

向いているタスク:

- 仕様とADRから実装タスクを分割する
- MVP仕様から実装用タスクファイルを作成する
- レガシーバッチをジョブ基盤へ移行する方針を作る
- 例外処理方針とエラーレスポンス仕様を整備する
- DB検索性能を調査し、インデックス設計を見直す
- 通知機能の構成を設計する
- 外部API連携のリトライ・タイムアウト方針を決める
- タスクに難易度、サイズ、推奨モデルを割り当てる

判断基準:

- コードを書く前に、何を正解にするか決める必要がある
- 実装順序や依存関係を整理する必要がある
- 仕様、ADR、MVP、制約条件を読み解く必要がある
- 失敗時の影響は中〜高だが、まだ GPT-5.5 を使うほどではない
- 既存コードが少なく、最初の骨格を決める段階

典型例:

- リポジトリに仕様とADRがある
- コードはほぼ無い
- これから作業を進めるためにタスク分割が必要
- 仕様はあるが、実装順序と粒度を決める必要がある

この場合、初手は GPT-5.4 が適切。仕様とADRがあるため GPT-5.5 ほどの未知は薄いが、タスク分割を誤るとプロジェクトの骨格がゆがむため、mini や Codex では軽すぎる。

### GPT-5.5

高リスク判断、難所突破、大規模設計、本番障害調査に使う。

向いているタスク:

- 本番環境で断続的に発生するタイムアウトの原因調査
- 本番環境で発生しているメモリリークの調査
- 認証・認可まわりの実装見直しと権限モデル再設計
- OAuth 2.0ベースの方式への移行
- 複数サービスに分散しているユーザー情報の統合方針設計
- モノリスから一部機能を独立サービスとして切り出す
- 既存アプリケーション全体をPort & Adapter構成へ再編する
- 仕様とADRに矛盾があり、設計判断をやり直す必要がある

判断基準:

- 失敗すると本番、セキュリティ、データ、運用に大きく影響する
- 原因や正解がまだ分からない
- 複数の技術領域をまたぐ
- 認証、認可、課金、DB移行、サービス境界に触る
- 実装より前に、調査計画や移行方針が必要
- 判断を間違えると後戻りが重い

GPT-5.5 を使いすぎない。仕様とADRが十分に詰まっていて、必要なのがタスク分割だけなら GPT-5.4 を優先する。

## Internal Questions

タスクを受け取ったら、内部的に次を確認する。

1. 仕様はすでに決まっているか？
2. 影響範囲は局所か？
3. 既存設計を読まないと壊すか？
4. 失敗したとき戻しやすいか？
5. 本番・認証・認可・DB・サービス境界に触るか？
6. 実装より先に設計判断が必要か？
7. 調査タスクか、実装タスクか？
8. コードが少ないだけで、初期設計が重いタスクではないか？
9. 仕様やADRに矛盾があるか？
10. 分割後に軽量モデルへ渡せるサブタスクへ落とせるか？

## Output Format

単一タスクの場合:

```md
## Classification

- Task type:
- Difficulty:
- Size:
- Complexity:
- Risk:
- Recommended model:
- Escalation model:
- Implementation model:
- Reason:

## Notes

-
```

複数タスクの場合:

```md
| No | Task | Type | Difficulty | Size | Risk | Recommended model | Escalation | Reason |
|---:|---|---|---|---|---|---|---|---|
| 1 |  |  |  |  |  |  |  |  |
```

必要に応じて、最後にモデル別の集計も出す。

```md
## Model Assignment Summary

| Model | Tasks |
|---|---|
| MAI-Code-1-Flash |  |
| GPT-5.4 mini |  |
| GPT-5.3-Codex |  |
| GPT-5.4 |  |
| GPT-5.5 |  |
```

## Examples

### 例1

タスク: README にローカル開発環境の起動手順を追記する

- Type: 定型作業
- Difficulty: 低
- Size: 小
- Risk: 低
- Recommended model: MAI-Code-1-Flash
- Reason: ドキュメント追記であり、仕様が明確なら深い設計判断が不要なため。

### 例2

タスク: 入力フォームの必須項目に未入力エラーを表示する

- Type: 局所実装
- Difficulty: 低
- Size: 小
- Risk: 低
- Recommended model: GPT-5.4 mini
- Reason: 対象フォームが限定されており、UIと軽いバリデーションの局所修正で済むため。

### 例3

タスク: FastAPI に新しい1エンドポイントを追加し、UseCase 経由で処理する

- Type: 構造を読む実装
- Difficulty: 中
- Size: 中
- Risk: 中
- Recommended model: GPT-5.3-Codex
- Reason: router、schema、UseCase、testなど複数ファイルにまたがり、既存の責務分離を読んで実装する必要があるため。

### 例4

タスク: 仕様とADRから、実装用のタスク分割ファイルを作成する。コードはほぼ無い。

- Type: 設計・分解
- Difficulty: 中〜高
- Size: 中〜大
- Risk: 中
- Recommended model: GPT-5.4
- Escalation model: GPT-5.5
- Implementation model: GPT-5.3-Codex
- Reason: 仕様とADRは存在するため最上位リスク判断を初手にする必要は薄いが、タスク分割を誤るとプロジェクト初期の骨格がゆがむ。実装ではなく、設計済み情報を作業順序へ変換するタスクなので GPT-5.4 が適切。

### 例5

タスク: 認証・認可まわりの実装を見直し、権限モデルを再設計する

- Type: 高リスク判断
- Difficulty: 高
- Size: 大
- Risk: 高
- Recommended model: GPT-5.5
- Implementation model: GPT-5.3-Codex
- Reason: 認証・認可はセキュリティとユーザー権限に直結し、設計を誤ると被害が大きい。まず GPT-5.5 で方針を決め、実装タスクへ分解してから Codex へ渡すべき。

## Guardrails

- モデルを過剰に上げない。
- 認証・認可、本番障害、DB移行、サービス分割、ユーザー情報統合は安全側に倒す。
- 「コードが少ない」ことを「簡単」と判定しない。
- 「仕様がある」ことを「実装だけ」と短絡しない。
- 仕様とADRがある場合は、まずそれらの整合性を確認する。
- 仕様やADRに矛盾がある場合は、GPT-5.5 への昇格条件として扱う。
- 実装タスクを巨大なまま出さず、Codex や mini に渡せる粒度へ分割する。
- 1タスクは、原則としてレビュー可能で、テスト可能で、完了条件が明確な単位にする。
