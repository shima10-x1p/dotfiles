# Model Routing Reference

この参照は、`SKILL.md` の判定を補助するためだけに読む。通常の分類は `SKILL.md` だけで完了してよい。

## 判定の優先順位

1. 高リスク領域に触るか: 本番障害、認証、認可、課金、セキュリティ、個人情報、DB移行、不可逆変更、サービス境界、ユーザー情報統合。
2. 仕様やADRに矛盾があるか: 矛盾があるなら GPT-5.5。整合していて分解が目的なら GPT-5.4。
3. 正解を決める必要があるか: 方針決定や実装順序の設計が必要なら GPT-5.4 以上。
4. 既存構造を読んで実装する必要があるか: 複数ファイル・複数層なら GPT-5.3-Codex。
5. 局所的で戻しやすいか: 1画面・1API・1関数に閉じるなら GPT-5.4 mini。
6. 完全に機械的か: 文言、typo、単純置換なら MAI-Code-1-Flash。

## 迷ったときの境界線

| 迷うケース | 判定 |
|---|---|
| 複数ファイルのtypoや文言統一 | MAI-Code-1-Flash |
| 1APIのレスポンス項目追加だが schema/test/router を触る | GPT-5.4 mini または GPT-5.3-Codex。層が増えたら Codex |
| UseCase、Repository、DBをまたぐ小機能 | GPT-5.3-Codex |
| 仕様とADRからタスク分割。コードはほぼ無い | GPT-5.4 |
| 仕様とADRが矛盾している | GPT-5.5 |
| 認証・認可の小修正 | 最低 GPT-5.3-Codex。設計判断があれば GPT-5.5 |
| 本番障害の原因が不明 | GPT-5.5 |
| DBインデックス追加の実装だけで方針決定済み | GPT-5.3-Codex |
| DB検索性能を調査してインデックス方針を決める | GPT-5.4。影響が本番重大なら GPT-5.5 |

## Difficulty / Size / Complexity / Risk の目安

| 軸 | 低 | 中 | 高 |
|---|---|---|---|
| Difficulty | 手順が明確で判断が少ない | 既存構造に合わせる判断がある | 正解や方針を決める必要がある |
| Size | 1ファイルまたは小変更 | 複数ファイル・1機能 | 複数機能・複数サービス・移行 |
| Complexity | 単純変更 | 複数層、テスト更新、軽い設計判断 | 不確実性、依存関係、競合制約が多い |
| Risk | 戻しやすい | ユーザー影響やデータ整合性に注意 | 本番、セキュリティ、データ、運用に重大影響 |

## 分割方針

GPT-5.4 または GPT-5.5 が選ばれる大きなタスクは、最後に下位モデルへ渡せる単位へ分割する。

- `MAI-Code-1-Flash`: 文言、設定、単純置換など、完了条件が一文で書けるもの。
- `GPT-5.4 mini`: 1画面、1API、1関数、1つの軽いバリデーションなど、局所でテストしやすいもの。
- `GPT-5.3-Codex`: router、schema、use case、repository、test など、既存構造を読んで実装する単位。
- `GPT-5.4`: ADRや仕様から順序、依存関係、タスク粒度、設計方針を決める単位。
- `GPT-5.5`: 矛盾解消、認証認可再設計、本番障害調査、サービス分割、データ統合など、判断の失敗コストが大きい単位。

## 出力時の注意

- `Recommended model` は、そのタスクの初手に使うモデルを書く。
- `Escalation model` は、不確実性や重大リスクが確認された場合の上げ先を書く。該当なしなら `なし`。
- `Implementation model` は、設計や調査を終えた後に実装へ落とすなら担当しやすいモデルを書く。実装タスクでない場合も、分解後の想定を書く。
- 不明点だけで停止せず、暫定判定と確認事項を分ける。
