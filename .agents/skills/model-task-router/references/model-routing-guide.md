# Model Routing Guide

## GPT-5.4 mini

GPT-5.4 mini は、判断より作業の比率が高いタスクに使う。

### 向いている条件

- やることが明確に決まっている
- 実装方針がすでに決まっている
- 変更対象が1ファイル、またはごく少数に絞られている
- 変更範囲が小さい
- 既存仕様を変えない
- 完了条件が明確
- テスト、型チェック、lint で成否を確認できる
- 失敗しても検出しやすい
- 失敗時の影響が小さい
- 既存コードの流儀に合わせればよい
- 最終レビューが人間または上位モデルによって行われる

### 代表例

- 1ファイル内の小さな修正
- 既存関数へのバリデーション追加
- 型エラー修正
- lint エラー修正
- テストが通るようにする最小修正
- TODO コメントに沿った実装
- 小さなUI調整
- ログ出力追加
- 定型的なデータ変換処理

### 判断基準

「何をするか」「どこを変えるか」「いつ完了か」が決まっているなら GPT-5.4 mini を選ぶ。

### reasoning effort

- 基本は `low`
- 少し複雑なら `medium`
- `high` 以上が必要そうなら、mini ではなく GPT-5.3-Codex 以上に上げる

## GPT-5.3-Codex

GPT-5.3-Codex は、実装だけではなく、コードベースを読んで少し判断する必要がある開発タスクに使う。

### 向いている条件

- タスクの目的は明確
- 変更対象をモデルに探させる必要がある
- 複数ファイルにまたがる可能性がある
- 既存コードの設計や流儀を読ませる必要がある
- 実装方針をある程度モデルに考えさせたい
- テスト追加やテスト修正を任せたい
- CI、型チェック、lint の失敗を調査させたい
- コードレビュー的な視点が必要
- 失敗してもテストやレビューで検出できる
- 仕様の大枠は決まっている
- 最終判断は人間または最上位モデルが行う

### 代表例

- 中規模機能追加
- 複数ファイルにまたがるバグ修正
- テスト失敗の原因調査と修正
- CI エラー修正
- 既存設計に沿ったリファクタリング
- API仕様に沿ったバックエンド実装
- フロントエンドとバックエンドをまたぐ小から中規模修正
- PRレビュー
- 既存コードの仕様調査
- ドキュメントと実装の整合性確認

### 判断基準

「何を作るか」は決まっているが、「どこをどう直すか」はコードを読んで判断する必要があるなら GPT-5.3-Codex を選ぶ。

### reasoning effort

- 軽い調査や差分説明: `low`
- 通常の実装、複数ファイル修正: `medium`
- 複雑なバグ調査、CI失敗分析、中規模リファクタ: `high`
- 長い調査、複数ステップの実装、大きめのコードベース理解: `xhigh`

## GPT-5.4以上の最上位モデル枠

最上位モデル枠は、曖昧さを整理し、設計し、判断するタスクに使う。固定の GPT-5.4 だけを意味しない。利用可能な最上位モデルが GPT-5.5 以降に更新された場合は、そのモデルをこの枠として扱う。

### 向いている条件

- 何をすべきか整理する必要がある
- 要件が曖昧
- 複数の実装方針を比較する必要がある
- 設計判断が必要
- アーキテクチャに関わる
- 複数モジュール、複数サービスにまたがる
- 長期的な保守性を考える必要がある
- 仕様の妥当性を検討する必要がある
- ユーザー体験への影響が大きい
- セキュリティ、認証、認可、課金に関わる
- 個人情報や機密情報の扱いに関わる
- DB設計やマイグレーションに関わる
- 本番障害や重大な不具合に関わる
- テストだけでは正しさを判断しにくい
- 失敗したときの影響が大きい
- 複数の資料やコードを横断して読む必要がある
- 実装前に計画を作りたい
- 実装後に高レベルレビューさせたい
- 下位モデルへ渡す実行タスクに分解したい

### 代表例

- 要件定義
- 仕様整理
- 技術選定
- アーキテクチャ設計
- 実装方針比較
- リスク分析
- セキュリティレビュー
- 認証・認可設計
- 課金処理の設計レビュー
- DB設計レビュー
- マイグレーション方針検討
- 本番障害の原因分析
- 大規模リファクタリング計画
- 複数サービスをまたぐ変更計画
- 設計ドキュメント作成
- 意思決定のための比較表作成
- 下位モデルに渡すタスク分解

### 判断基準

「何を、なぜ、どこまでやるか」を考える必要があるなら最上位モデル枠を選ぶ。

### reasoning effort

- 軽い相談や比較: `low`
- 通常の設計相談、仕様整理、実装方針比較: `medium`
- 影響範囲の広い設計判断、複雑な不具合分析: `high`
- 重大な意思決定、大規模アーキテクチャ検討、深いリスク評価: `xhigh`

## Forced Escalation

以下に1つでも当てはまる場合は、GPT-5.4 mini には割り当てない。

- 認証
- 認可
- 課金
- セキュリティ
- 個人情報
- 機密情報
- DBスキーマ変更
- 不可逆なマイグレーション
- 本番障害
- データ損失の可能性
- 外部API仕様の変更
- 公開APIの破壊的変更
- テストだけでは正しさを確認できない変更

このうち、影響範囲が広いもの、設計判断が必要なもの、失敗時の影響が大きいものは最上位モデル枠へ上げる。目的が明確で、変更範囲が限定され、テストやレビューで失敗を検出できる場合は GPT-5.3-Codex を候補にする。

## Confidence Guidance

- `高`: 入力に目的、対象範囲、方針、完了条件、検証方法、リスク情報が揃っている
- `中`: 主要情報はあるが、対象範囲、検証方法、リスクのどれかが不足している
- `低`: 目的や影響範囲が曖昧、または重大リスクの有無が不明

## Routing Heuristics

- mini を選ぶのは、作業対象と完了条件が明確で、失敗が検出しやすいとき。
- Codex を選ぶのは、目的は明確だが、コードを読んで変更箇所や実装方法を判断する必要があるとき。
- 最上位モデル枠を選ぶのは、要件、設計、リスク、影響範囲、分解方針を考える必要があるとき。
- `難しいから最上位` とは判定しない。検証可能で仕様が固まっている複雑な作業は GPT-5.3-Codex でもよい。
- `小さいから mini` とは判定しない。認証、課金、DB、本番障害などに関わる小変更は上位に上げる。
- テストで検出できる失敗と、検出しにくい失敗を同列に扱わない。
